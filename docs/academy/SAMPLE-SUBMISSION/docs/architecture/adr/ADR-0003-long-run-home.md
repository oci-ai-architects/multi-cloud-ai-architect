# ADR-0003: Railway worker for long runs, Vercel for the portal, Cloudflare at the edge

Status: accepted 2026-09-29 · Decision: run · Owner: platform engineer

## Context

OCR on a 30-page scanned invoice plus two model calls and matching takes up to 3 min 40 s in the
fixture backfill. The portal needs fast page loads and nothing long-running. Email ingestion must
never lose a message, including when the worker is down. The firm has no cloud team; whatever is
chosen is operated by one platform engineer.

## Options considered

1. **Everything on Vercel**: portal on Next.js, long work in Vercel Workflow (durable steps,
   retries). One provider, one bill, good DX. A reasonable engineer would pick this.
   Rejected for now: matching runs transactions against Postgres, and the team wants the queue and
   the data in one Postgres they can `psql` into; that pushes toward an external database anyway,
   and the split then exists regardless. Also rejected because the credential review asks for a
   deliberate two-provider split, and this ADR records that as a reason.
2. **Everything on Cloudflare**: Email Worker, Agents SDK on Durable Objects for state, Workflows
   for steps, D1 for data. Strong for ingestion and per-invoice state. Rejected: PO and receipt data
   is relational with joins the team already writes in Postgres, and the OCR library needs a
   container runtime.
3. **Split by plane**: Cloudflare Email Worker for ingress (stores raw mail in R2, then enqueues);
   Railway runs the durable worker and Postgres (queue, invoices, audit); Vercel serves the portal,
   which reads Postgres through a narrow API on the worker.

## Decision

Option 3. Each provider owns one plane: Cloudflare the edge and ingress, Railway the long-run home
and state, Vercel the experience plane. The model seam (ADR-0004) routes through Cloudflare AI
Gateway, so model traffic is observed in one place whichever worker calls it.

## Consequences

- Accepted cost: three dashboards, three sets of credentials, and an authenticated hop between
  Cloudflare and Railway. The runbook carries one rollback command per provider.
- If Railway is down, Cloudflare keeps accepting mail into R2 and a dead-letter queue; nothing is
  lost, it only waits (runbook check `ingest-dlq-empty`).
- Portability: the worker is a plain Node container; moving it to Cloud Run is a deploy change,
  not a code change. Not tested.

## What would reverse this

If the platform engineer spends more than 4 hours a month on cross-provider operations (tracked in
the runbook's ops log), consolidate onto Vercel Workflow plus a managed Postgres, accepting option 1.

## Acceptance eval

`gold-05`, `edge-01`: pass when run against the deployed worker, and the restart test in the
runbook (kill the worker mid-run, job resumes from its last step) passes on the fixture deploy.
