Spec, decide, draw, evaluate, deploy.

Five stages in a fixed order, with one gate. Each stage builds on published work, linked in the stage. The method's own rule joins them: an architecture decision counts as accepted only when its eval passes.

Status: the method is written and has not yet been run end to end on a reviewed design. The first sample design, assessed against the published rubric, comes before the academy opens.

The five stages

Stage 1Spec

One spec per change: the problem, who has it, the constraints, what is out of scope, and a budget for the qualities that matter to agents, such as latency, cost per task and where data may live.

You produce
spec.md, short enough to review in one sitting.
Done when
Every requirement traces to a decision or a test.
Builds on
Spec Kit and OpenSpec. The file stays readable by both.

Size matters. Birgitta Böckeler watched one tool turn a single bug into four user stories and sixteen acceptance criteria. A spec should be as large as the change, and no larger. Read her review.

Stage 2Decision record

One ADR per consequential choice. The first one is usually the cheapest to get right: does this need an agent at all, or will a single model call or a fixed workflow do? Azure's guidance puts it as using the lowest level of complexity that reliably meets the requirements.

You produce
adr/NNNN-title.md with context, options, decision, consequences and the eval that accepts it.
Done when
The acceptance eval is named, has a threshold, and can run.
Builds on
The decisions section of arc42, Anthropic's workflow and agent patterns, and the Azure complexity ladder.
# Example only. Names and thresholds are illustrative.
# ADR 0003: Route refund requests through a fixed workflow

Status: proposed
Context: Refunds follow policy with three branches. Errors cost money.
Options: single agent with tools; routing workflow; human queue.
Decision: routing workflow. An agent only drafts the customer reply.
Consequences: less flexible on edge cases; every branch is testable.

Acceptance eval: evals/refund-routing.yaml
  - routes each of the 120 labelled cases to the policy branch
  - threshold: 118 of 120 correct, zero refunds above policy limit
  - runs in CI on every change to the workflow or its prompts
Stage 3C4 agentic views

Context and container diagrams in standard C4, with the parts agents add drawn as first-class elements: the agent runtime, tool access through MCP, memory, the model endpoint, the eval harness, and the trust boundary they cross.

You produce
Context and container views as code, so they diff and review like everything else.
Done when
Every arrow that crosses the trust boundary has an owner and a control.
Builds on
The C4 model and current research applying C4 to agentic systems.
Stage 4Evals

Graders for each decision, checking outcomes and, where it matters, the path the agent took to get there. They run in CI. A pass accepts the ADR. A fail sends the work back to the decision: the method treats a failed eval as a design question before it treats it as a prompt problem.

You produce
An eval suite per ADR, with labelled cases and a threshold.
Done when
Every proposed ADR is either accepted by a green run or revised.
Builds on
Anthropic's guide to agent evals and the AI Evals course from Husain and Shankar.
Stage 5Deploy

The same design deployed on at least two platforms. Where the platforms force a difference, that difference becomes its own ADR, so the next team can see what was a choice and what was a constraint.

You produce
Two working deployments and the ADRs that explain where they differ.
Done when
Both pass the same eval suite.
Builds on
The AWS Agentic AI Lens as a review checklist, Google's pattern decision guide, and the per-platform packs in the kit.

What the method leaves to others

Protocols belong to their foundations: MCP and A2A are governed under the Linux Foundation's Agentic AI Foundation. Model behaviour is best explained by the labs that train the models. Framework tutorials are well covered elsewhere. The method uses all of these and owns none of them.
